# تشغيل PDF Control عبر Phoenix LiveView — 2026-10-21

## النتيجة والنطاق
تطبيق Phoenix/Elixir في `web/` يخدم الصفحة الرئيسية واتصال LiveView وأصول الواجهة وطلبات المعالجة. بقي محرك PDF الحالي داخل عامل Python مستمر بلا خادم HTTP ثانٍ. جميع أدوات الواجهة الـ12 محفوظة. محرر الطبقات والسحب والتكبير والتراجع وعرض المعاينات تبقى JavaScript داخل hook مع `phx-update="ignore"`؛ هذا انتقال للتطبيق، وليس ادعاء إزالة JavaScript أو إعادة كتابة حسابات PDF بـElixir.

لا يتغير مسار الإنتاج السابق تلقائيًا. أمر Project Manager الحالي يبني wheel ويشغّل واجهة Python القديمة؛ لا يصلح وحده لنشر حزمة LiveView الجديدة. إضافة مشغّل الحزمة والـWebSocket واختبارات الجلسات والاسترجاع في مدير المشاريع عمل تكامل مطلوب قبل النشر. مصدر المدير خارج نطاق الكتابة لهذه المهمة. لا commit أو push أو نشر أو تغيير صلاحيات من هذه المهمة.

## التشغيل المحلي المتحقق
من PowerShell على Windows:
```powershell
wsl.exe -d Rpdf-dev --cd /home/rpdf/rpdf --exec env PHX_SERVER=true PORT=4000 sh scripts/liveview.sh phx.server
```
الصفحة المحلية بعد التحقق: http://localhost:4000/

البرنامج يستخدم البيئة المعزولة داخل `.runtime/elixir` أو أدوات Elixir الموجودة في PATH. يحفظ Hex/Mix/cache داخل `.runtime` ولا يغير PATH الدائم. يحتاج Python الموجود في `.venv` مع تبعيات المشروع. مصدر النصوص والتنسيق هو الملفات الحالية في `src/pdf_control/static`؛ لا نسخة محرر متفرعة يصعب مزامنتها.

## الفحوص
داخل مصدر المشروع في Rpdf-dev:
```sh
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check .
sh scripts/liveview.sh check
.venv/bin/python tools/liveview_acceptance.py http://127.0.0.1:4000
TESSDATA_PREFIX="$PWD/.runtime/tessdata" .venv/bin/python tools/liveview_accuracy.py
.venv/bin/python tools/liveview_load.py
```
نتائج التحقق: 75 اختبار Python، و8 اختبارات ExUnit/LiveView، و15 طلب قبول عبر HTTP للتحقق من جميع وظائف المعالجة. اختبار ضغط اصطناعي واحد: 20 طلب OCR، قُبلت 8 ورُفضت 12 بـ503؛ فحص الصحة 104 عينات، median 2.232 ms وmax 12.558 ms. هذه ليست سعة إنتاج معلنة أو مقارنة أداء إحصائية.

عينة عربية اصطناعية واحدة أعطت الحقول وصور الصفحات نفسها عبر المحرك المباشر والمسار الجديد؛ CER=0 على تلك العينة فقط. لا تعمم النتيجة على المستندات الحقيقية أو الكتابة اليدوية.

اختبار المتصفح أكد اتصال LiveView، بدء hook، الإنجليزية/العربية، والمظهرين بصريًا. رفع الملفات في IAB فشل قبل وصول الطلب إلى الخادم؛ Chrome المحلي رفض الرفع الآلي لأن وصول الإضافة للملفات المحلية غير مفعل. لم تُغيّر هذه الصلاحية ولم يُتجاوز الحظر. لذلك يظل نجاح رفع/تنزيل الملف من واجهة المتصفح غير مؤكد؛ HTTP الحقيقي والتنزيل وPDF الناتج اختُبرت آليًا بالكامل.

## إعدادات التشغيل
- `PDF_CONTROL_ROOT`: مصدر الأصول الثابتة؛ افتراضيًا جذر المشروع، أو مجلد app في الحزمة.
- `PDF_CONTROL_PYTHON`: Python الذي يحتوي المحرك؛ الافتراضي .venv/bin/python.
- `PDF_CONTROL_SPOOL`: جذر ملفات الربط المؤقتة؛ معرف عشوائي مستقل لكل طلب. الملفات الجديدة لهذا الطلب فقط تُنظف بعد الرد.
- `PDF_CONTROL_MAX_QUEUE`: 8 مهام تشمل النشطة والمنتظرة افتراضيًا. المعالجة عامل واحد تسلسلي، لتثبيت الجلسات وعزل الحمل؛ ليس pool متعددًا أو قدرة توازٍ غير محدودة.
- `PDF_CONTROL_JOB_TIMEOUT_MS`: 300000 افتراضيًا. توقف العامل يفشل الطلبات المعلقة دون إعادة تشغيل المهمة تلقائيًا.
- حدود الملف/المهمة/الصفحات/DPI وOCR الأصلية بقيت في محرك Python. حدود رفع Phoenix تضيف مساحة صغيرة لتغليف multipart، ولا توسع حدود الملفات الفعلية.
- تفضيلات اللغة والمظهر والتخزين المحلي للمحرر تستخدم المفاتيح الحالية.
- جلسات المعاينة مرتبطة بمساحة العمل الموقعة؛ توكن مساحة أخرى يرفض. إعادة تشغيل العامل تفقد جلسات المعاينة المؤقتة، ويعيد المتصفح تحميلها وفق سلوك الاستعادة السابق.
- حالة المهمة الأخيرة مستقلة عن اتصال LiveView، بحد ذاكرة وزمن احتفاظ ساعة، ولا تحتوي أسماء أو محتوى المستندات. ليست سجلاً دائمًا للمهام ولا ضمان استئناف OCR بعد انهيار العامل.
- ملفات العربية المحلية في .runtime/tessdata. نموذج ara الرسمي من tessdata_fast/4.1.0، SHA256: e3206d3dc87fd50c24a0fb9f01838615911d25168f4e64415244b67d2bb3e729. النسخة الإنجليزية من النظام محفوظة في المجلد نفسه. لا يتغير اختيار OCR الافتراضي eng.
- `SECRET_KEY_BASE` و`PHX_HOST` لازمان لتشغيل إصدار prod. لا تطلب أو تحفظ أسرارًا في السجل؛ تزودها إدارة الهدف عبر إعداداتها المعتمدة.

## الحزمة المحلية
```sh
MIX_ENV=prod sh scripts/liveview.sh release
.venv/bin/python tools/package_liveview.py --output .runtime/new-reviewed-bundle
```
أداة الحزمة ترفض استبدال مجلد موجود. تحتوي BEAM release وwheel المحرك وrequirements-runtime.lock والأصول المجمدة وmanifest للبصمات. تستبعد ملفات BEAM COOKIE؛ مشغّل الحزمة يعطل distributed Erlang لأنه غير لازم للإشراف بنظام التشغيل. لا تحتوي بيئة .venv أو نماذج OCR أو أسرار إنتاج.

الحزمة المتحققة في هذه المهمة: `.runtime/liveview-bundle-20261021-v2`. ثُبّت wheel الخاص بها في بيئة `.runtime/bundle-test-venv` الجديدة، وأُقلعت الحزمة من أصولها نفسها على loopback:4002 بقيم اختبار فقط؛ نجحت طلبات القبول الـ15. لا اعتماد على تثبيت editable للمحرك في اختبار الحزمة. البصمات في manifest.json، والمصدر موسوم worktree_dirty=true بصدق؛ ليست إصدارًا منشورًا من commit نظيف.

لتركيب الحزمة على هدف مستقبلي: تجهيز Python المتوافق وتبعيات lock وTesseract/الخطوط؛ تثبيت wheel في venv جديدة؛ توفير سر الجلسة واسم المضيف وموضع spool؛ تشغيل run.sh بخدمة موازية على loopback؛ تهيئة nginx HTTP/WebSocket والتحقق من الأصل وTLS ومنع التخزين المؤقت للأصول غير المرقمة؛ فحص الجلسات والقبول ثم التحويل المراقب وخطة العودة. هذه تعليمات تجهيز، لا تحقق تنفيذ على الإنتاج.
